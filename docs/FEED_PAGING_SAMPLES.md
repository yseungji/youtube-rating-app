# 내 계정으로 피드 페이징 확인

2026-11-16 사용자 실행 확인: 샘플 생성 success=45, skipped=0, failed=0. 인기순은 added=20/20/6, total=20/40/46, 마지막 hasMore=false로 조회됐다. 사용자가 전체 표시도 정상이라고 확인했다. 기존 공개 평가 1개가 함께 포함된 것으로 보인다. 샘플 삭제·서로 다른 좋아요 수의 정렬·최신순 다중 묶음 병합은 이 로그로 검증하지 않았다. 에이전트가 생성·삭제나 테스트를 직접 실행한 것은 아니다.

## 인기순 실행 순서

1. 디버그 앱에서 사용할 본인 계정으로 로그인한다.
2. 개발 메뉴의 Cloud Firestore 화면(CloudFirestoreActivity)을 연다.
3. **내 계정에 샘플 평가 45개 생성**을 누르고 작업이 끝날 때까지 기다린다.
4. 성공 45개·실패 0개를 확인한다. 이미 생성된 문서는 건너뛴다. 일부 실패했다면 Logcat에서 원인을 확인하고 다시 생성할 수 있다.
5. 메인 피드에서 **인기순**을 선택하고, 맨 위에서 아래로 당겨 새로고침한다.
6. 끝까지 스크롤하며 샘플 번호 01~45가 중복·누락 없이 나타나는지 확인한다.
7. 확인 후 같은 계정으로 개발 화면의 **내 계정의 페이징 샘플만 삭제**를 누르고 피드를 새로고침한다.

화면을 열기만 해서는 저장하지 않는다. 기존 실제 영상 샘플 1개 기능은 별도 버튼에 남겨뒀다.

## 샘플 범위

- ratings/{본인 UID}_paging-sample-v1-01 ~ 45에 공개 평가를 만든다.
- 서로 다른 가상 영상 ID를 사용한다. 기존 실제 영상 평가와 분리하며, 생성 전 서버에 문서가 존재하면 덮어쓰지 않고 건너뛴다.
- 별점은 1~5를 반복하고 한줄평에 샘플 번호를 표시한다. 작성 시각은 서버가 채운다.
- 좋아요·댓글 수는 모두 0이다. 같은 정렬값의 페이지 경계에서 중복·누락이 없는지 확인하는 용도이며, 서로 다른 좋아요 수의 인기 정렬 검증은 포함하지 않는다.
- videos·users·follows 문서는 생성·수정하지 않는다. 실제 YouTube API도 호출하지 않는다.
- 디버그 피드는 샘플을 가상 영상으로 표시하고 상세 진입을 하지 않는다. 실제 영상 재생·상세 평가 검증용 데이터는 아니다.
- 공개 ratings를 사용하므로 다른 사용자에게도 보일 수 있다. 확인 후 정리한다.
- 위 인기순 샘플에는 팔로잉 30명 초과 병합 검증이 포함되지 않는다. 아래 최신순 샘플을 별도로 사용한다.

## 팔로잉 최신순 샘플 — 끝까지 페이징 사용자 확인

2026-11-16 사용자 로그로 authors=31, groups=2 및 첫 페이지20개 조회를 확인했다. 인덱스 오류 해소 후 사용자가 끝까지 정상 표시됐다고 확인했고, 제공 화면에서 순서61/62와62/62를 확인했다. 마지막 로그는 group=1, received=0, exhausted=true 및 added=2, total=62, hasMore=false로 조회 종료를 확인했다. 비공개/미팔로우 제외 조건의 개별 화면 확인과 샘플 삭제는 별도로 남아 있다. 에이전트가 테스트를 직접 실행한 것은 아니다.

실제 로그인 계정은 추가하지 않는다. 현재 로그인 계정의 UID로 구분되는 가상 작성자·프로필·평가·팔로우 문서를 만든다. 다른 UID의 문서 생성이 현재 서버 규칙에 허용되지 않으면 실패한다. 보안 규칙을 바꾸거나 관리자 권한으로 우회하지 않는다.

1. 같은 계정으로 로그인하고 DevMenuActivity → Cloud Firestore를 연다.
2. **팔로잉 31명·최신순 샘플 생성**을 누르고 완료를 기다린다.
3. 처음 실행은 success=127, skipped=0, failed=0이 예상된다. 전체 127개는 프로필32 + 평가64 + 팔로우31 문서다. 재실행 시 기존 샘플은 건너뛰며 덮어쓰지 않는다.
4. 피드에서 **최신순**을 선택하고 당겨서 새로고침한 뒤 끝까지 내린다.
5. 확인 후 같은 개발 화면의 **이번 계정의 팔로잉 샘플만 삭제**를 누르고 피드를 새로고침한다.

검증할 내용:

- 팔로우한 작성자31명의 공개 평가62개가 샘플 순서01→62로 표시된다. 작성자31의 평가가 순서01과32에 있어 두 조회 묶음의 결과를 섞어야 한다.
- 샘플만 대상이면 total=20→40→60→62, 마지막 added=2와 hasMore=false가 예상된다. 기존 팔로잉의 평가가 있으면 총개수는 늘어나고 중간에 섞일 수 있다.
- 미팔로우 작성자32의 공개 평가1개와 팔로우 작성자01의 비공개 평가1개는 최신순에 표시되면 안 된다. 두 문서는 정상 샘플보다 최신 시각으로 만들어 필터 누락을 쉽게 찾는다.
- 미팔로우 작성자의 공개 평가는 전체 공개 평가를 읽는 인기순에 나오는 것이 정상이다.
- 표시 순서는 댓글의 `[팔로잉샘플 v1] 순서 NN / 62`로 확인한다. 작성 시각은 2026-11-16 00:00 KST부터 1분 간격으로 고정해 일부 생성 후 재시도해도 순서가 유지된다.
- 이 데이터는 관계 문서에 따른 피드 조회 검증용이다. Authentication 로그인·회원가입, 프로필 팔로워/팔로잉 집계 수치, Security Rules의 접근 차단 검증을 완료한 것은 아니다. 기존 본인 프로필·기존 팔로우·videos·usernames는 수정하지 않는다.
- 비공개 평가를 포함해 다른 UID 문서의 사전 조회가 막히면 일부 생성/삭제만 성공할 수 있다. 실패가 남은 상태에서 예상62개 검증을 완료 처리하지 않는다. 이후 별도 테스트 환경이나 관리자가 준비하는 시드 방식을 검토한다.
- 정리 대상은 이번 계정용으로 정해진127개 ID뿐이며, sampleSet과 sampleOwnerUid가 일치할 때만 삭제한다. 반응 수가 생긴 평가는 건너뛴다. 이 버튼은 이전 인기순45개 샘플 삭제 버튼과 별개다.

최신순 Logcat 필터:

```text
package:com.example.viewit (tag:FollowingFeedSample | tag:FeedRepository | tag:FeedFragment) level:DEBUG
```

팔로잉이 샘플31명뿐이면 `팔로잉 조회 완료: authors=31, groups=2`를 확인한다. 묶음 조회의 hasCursor=false는 첫 조회, true는 그 묶음의 마지막 문서 다음부터 읽는 조회다. 기존 팔로잉 수에 따라 묶음 수·구성은 달라질 수 있다.

`PERMISSION_DENIED`는 샘플 생성 권한 문제다. `FAILED_PRECONDITION: The query requires an index`라면 Logcat의 Firebase 콘솔 링크에서 해당 인덱스를 준비해야 한다. 최신순 인덱스 정의는 firestore.indexes.json에 있으나 서버 반영은 별도로 확인한다.

## 인기순 Logcat

```text
package:com.example.viewit (tag:FeedPagingSample | tag:FeedFragment) level:DEBUG
```

생성 완료 예: 샘플 작업 종료: success=45, skipped=0, failed=0

피드에는 한 번에 최대 20개가 전달된다. 공개 평가가 샘플 45개뿐이면 대략 다음 로그를 확인한다.

```text
피드 조회 성공: added=20, total=20, hasMore=true
피드 조회 성공: added=20, total=40, hasMore=true
피드 조회 성공: added=5, total=45, hasMore=false
```

기존 공개 평가도 함께 조회되므로 실제 total과 마지막 added는 더 클 수 있다.
현재 목록이 화면을 채우지 못하면 기존 로직이 다음 페이지를 자동으로 읽을 수 있다.
샘플의 좋아요 수가 모두 같아 샘플끼리는 문서 ID 내림차순(45 → 01)으로 표시된다. 다른 공개 평가가 사이에 들어갈 수 있다.

## 삭제와 실패 처리

삭제는 위 45개 ID만 읽고, 본인 UID·샘플 표시·영상 ID가 일치하는 경우에만 수행한다. 좋아요·댓글 수가 0이 아닌 문서는 건너뛴다. 다른 계정의 샘플과 기존 실제 영상 평가는 삭제 대상이 아니다.
여러 쓰기를 하나로 묶는 방식이 아니므로 일부만 성공할 수 있다. 실패 개수와 Log.e()를 확인한다.
PERMISSION_DENIED가 나오면 현재 서버 보안 규칙을 확인해야 한다. 이 기능을 위해 규칙을 변경하거나 우회하지 않는다.
진행 중 화면을 닫거나 회전하면 상태 안내가 초기화될 수 있으므로 작업 종료를 기다린다. 다시 생성하면 이미 존재하는 ID는 건너뛴다.
